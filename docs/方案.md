**三个必须先接受的事实：**

1. `EXTRA_SKIP_UI` 官方定义原文是 "the application is **asked to** bypass any intermediate UI"。**被请求**，不是被强制。手机厂商的时钟 App 可以不遵守。
2. 部分国产 ROM（小米 HyperOS / 华为 HarmonyOS / 部分 OPPO、vivo）会忽略 `SKIP_UI`，仍弹出时钟界面。这是**正常且预期**的行为，不是 bug。
3. **降级路径才是这个 App 的主路径。** 一键设置是加分项，预填 + 用户按保存是保底项。两条路都必须实现。

## 1. 推荐技术栈

### 1.1 为什么是原生 Kotlin + Compose

评估了四条路线：

| 方案 | 流畅度 | 调用系统闹钟 | 体积 | 判定 |
|---|---|---|---|---|
| **原生 Kotlin + Compose** | ★★★★★ | 直接 `startActivity` | ~3 MB | ✅ **推荐** |
| 原生 Kotlin + View/XML | ★★★★☆ | 同上 | ~2 MB | 可行，但没有理由退回 |
| Flutter | ★★★★☆ | 需写 PlatformChannel 桥接 | ~20 MB | ❌ 为一个 Intent 引入整个引擎 |
| React Native / WebView | ★★★☆☆ | 桥接更麻烦，冷启动慢 | ~30 MB+ | ❌ 与「流畅」直接冲突 |

关键理由只有一条：**这个 App 的 90% 价值是一个 Intent 调用。** 原生 Kotlin 直接 `startActivity(intent)`，零桥接、零序列化、零引擎启动开销。引入 Flutter 意味着为了一个 20 行的功能，背上 20 MB 的运行时。

`EXTRA_SKIP_UI` 这条路，第三方框架全部要靠 PlatformChannel / NativeModule 绕出去，中间任何一层出错都会变成"点了没反应"。原生让失败点收敛到一个 `try/catch`。

### 1.2 流畅度怎么保证

这个 App 只有一个"实时"需求：秒级刷新的时间显示。做得不好会掉帧、费电。三条规矩：

1. **用 `produceState` + `delay` 做 1 秒心跳，不用 `Handler.postDelayed` 递归。** Compose 的协程会在 Activity 进入后台时自动取消（配合 `repeatOnLifecycle` 或 `LaunchedEffect`），不需要手动 `onStop` 里摘 handler。
2. **心跳对齐整秒。** 不要 `delay(1000)` 死循环——那会累积漂移，导致秒数跳变。每次计算「距离下一个整秒还差多少毫秒」，睡那个时长。
3. **起床时间只在秒变化时重算，且 1–9 周期一次性算完。** 9 行 × 6 次算术运算，单帧耗时 < 0.1 ms。这个量级不需要缓存、不需要 `remember` 复杂化。

### 1.3 为什么 minSdk = 26

| 候选 | 理由 |
|---|---|
| minSdk 21 | 覆盖更老设备，但要为通知渠道、时区 API、`java.time` 做兼容分支 |
| **minSdk 26** ✅ | `java.time`（`LocalDateTime` / `ZonedDateTime`）原生可用，**不需要 desugaring**；通知渠道 API 原生可用 |
| minSdk 31 | 太激进，无必要 |

关键在 `java.time`。R90 计算要处理跨天、时区、12/24 小时制，用 `java.util.Calendar` 写会非常痛苦且容易错。minSdk 26 让 `java.time` 直接可用，**这是本方案最重要的一个版本决策**。你自己的手机远超这个版本，没有任何代价。

### 1.4 为什么 targetSdk = 35

- Google Play 从 2025-08 起要求新应用 targetSdk ≥ 35。就算只自用，也用最新版避免将来被系统行为变更打脸。
- targetSdk 35 引入了对 `SCHEDULE_EXACT_ALARM` 的更严限制（默认拒绝）——**但本方案完全不需要这个权限**，因为我们不自己设闹钟，只把活交给系统时钟。这是架构上天然规避。
- 需要处理的 targetSdk 31+ 变更：`android:exported` 显式声明（本方案只有一个 Launcher Activity，写 `exported=true`）。
- 需要处理的 targetSdk 30+ 变更：包可见性 `<queries>`（见第 6 节）。

## 2. 系统闹钟可行性

### 2.1 官方 API 事实（逐条核对自 Android Developers 文档）

| 项 | 事实 | 来源 |
|---|---|---|
| Action 常量 | `AlarmClock.ACTION_SET_ALARM`，值 `"android.intent.action.SET_ALARM"` | API 9+ |
| `EXTRA_HOUR` | `"android.intent.extra.alarm.HOUR"`，Integer，**ranges from 0 to 23** | API 9+ |
| `EXTRA_MINUTES` | `"android.intent.extra.alarm.MINUTES"`，Integer，0–59，默认 0 | API 9+ |
| `EXTRA_MESSAGE` | `"android.intent.extra.alarm.MESSAGE"`，String，闹钟标签 | API 9+ |
| `EXTRA_SKIP_UI` | `"android.intent.extra.alarm.SKIP_UI"`，Boolean，默认 **false** | API 11+ |
| `EXTRA_IS_PM` | `"android.intent.extra.alarm.IS_PM"`，Boolean。**Used by `ACTION_DISMISS_ALARM`** —— 不是 SET_ALARM 的参数，不要传 | API 23+ |
| `EXTRA_DAYS` | `"android.intent.extra.alarm.DAYS"`，ArrayList\<Integer\>，重复闹钟 | API 19+ |
| `EXTRA_RINGTONE` | `"android.intent.extra.alarm.RINGTONE"`，String（URI 或 `VALUE_RINGTONE_SILENT`） | API 19+ |
| `EXTRA_VIBRATE` | `"android.intent.extra.alarm.VIBRATE"`，Boolean，默认 true | API 19+ |
| 权限 | `com.android.alarm.permission.SET_ALARM` | 普通权限 |

**官方对 `EXTRA_SKIP_UI` 的原文（不可绕过的事实）：**

> Bundle extra: Whether or not to display an activity after performing the action. Used by ACTION_SET_ALARM and ACTION_SET_TIMER. If true, the application **is asked to** bypass any intermediate UI.

注意 `is asked to`。这是**请求语义**，厂商实现有权拒绝。

**官方对 `ACTION_SET_ALARM` 的完整行为定义（关键，很多人不知道）：**

> Activates an existing alarm or creates a new one. This action requests an alarm to be set for a given time of day.
> - **If no time of day is specified**, an implementation should start an activity that is capable of setting an alarm (`EXTRA_SKIP_UI` is ignored in this case).
> - If a time of day is specified, and `EXTRA_SKIP_UI` is true, and the alarm is not repeating, **the implementation should remove this alarm after it has been dismissed**.
> - If an identical alarm exists matching all parameters, the implementation may re-use it instead of creating a new one (in this case, the alarm should not be removed after dismissal).
> - **This action always enables the alarm.**

这三条推论非常重要：

- **不传 `EXTRA_HOUR` 时 `SKIP_UI` 会被忽略。** 所以一键设置**必须**同时传 `EXTRA_HOUR` 和 `EXTRA_MINUTES`。
- **`SKIP_UI=true` 的一次性闹钟，响完即自动删除。** 对你的使用场景是好事——不会在系统时钟里堆一堆历史闹钟。
- **Action 会自动启用闹钟。** 不需要额外调什么"启用"接口。

### 2.2 「一键直接设置」到底能不能成

`EXTRA_SKIP_UI = true` **可以**实现一键直接设置，条件是：

| 条件 | 说明 |
|---|---|
| 设备上存在响应 `ACTION_SET_ALARM` 的时钟 App | 绝大多数手机有 |
| 该 App 遵守 `SKIP_UI` | AOSP DeskClock **遵守** |
| 同时传了 `EXTRA_HOUR` | **必须**，否则 `SKIP_UI` 被忽略 |
| 你的 App 处于前台 | Android 10+ 限制后台启动 Activity；用户在 App 里点按钮，天然满足 |

**AOSP / Google 时钟（`com.google.android.deskclock`）的实现证据：**
AOSP DeskClock 的 `HandleApiCalls` Activity 声明为 `android:theme="@android:style/Theme.NoDisplay"` + `launchMode="singleInstance"` + `taskAffinity=""`，专门用于无界面执行 API 调用。`SET_ALARM` 走 `HandleSetAlarmApiCalls` 这个 activity-alias，在 Manifest 层用 `android:permission="com.android.alarm.permission.SET_ALARM"` 做权限校验。**只有一个歧义情况会弹 UI**：当请求匹配到多个闹钟需要用户选择时，会拉起 `AlarmSelectionActivity`。设置新闹钟不触发这条路径。

**哪些设备可能失败（不遵守 `SKIP_UI`）：**

| 厂商 / 系统 | 预期行为 | 置信度 |
|---|---|---|
| AOSP / Pixel / LineageOS | 遵守 `SKIP_UI`，真正一键 | 高 |
| **OPPO ColorOS（本机）** | **✅ 实测遵守** —— 一键无 UI，无界面弹出 | **已实测**（PMB110 / ColorOS 16.0.9.400） |
| 小米 MIUI / HyperOS | **倾向忽略 `SKIP_UI`**，打开时钟界面 | 中（待真机验证） |
| 华为 EMUI / HarmonyOS | **倾向忽略**，且华为可能不带 AOSP 时钟 | 中（待真机验证） |
| vivo OriginOS | 行为不一，多数会弹界面 | 低（待真机验证） |
| 三星 One UI | 通常遵守，三星时钟 `com.sec.android.app.clockpackage` | 中（待真机验证） |
| Android TV | **可能完全不支持** alarm intents（官方明示） | 高 |

> 标注「待真机验证」的项，必须在你的手机上实测。
>
> **本机的实测已经做完**，完整证据链见 `docs/真机验证-ColorOS16-SKIPUI.md`。摘要：

| 组 | `SKIP_UI` | 顶层 Activity | 闹钟是否写入 |
|---|---|---|---|
| 基线 | — | 无变化 | — |
| 测试组 | `true` | **无变化（无界面）** | ✅ 已写入 21:37 |
| 对照组 | `false` | 变为 `AlarmClockCTS`（界面弹出） | 等用户保存 |

> 对照组的存在是关键 —— 它排除了「设备锁屏导致所有 Activity 都看不见」这个混淆因素。

### 2.3 三层降级策略（本方案的核心设计）

```
Level 1：EXTRA_SKIP_UI = true
         ↓ 无法验证是否生效（Intent 发出去就不知道结果了）
Level 2：EXTRA_SKIP_UI = false → 系统时钟打开，时间已预填，用户按保存
         ↓ 若 ActivityNotFoundException / 无 handler
Level 3：找不到任何能处理 SET_ALARM 的 App
         → 弹对话框：明示原因 + 三条补救路径
           （打开时钟列表 / 查时钟应用是否被禁用 / 复制时间）
           不装作成功，也不只甩一句"失败"
```

> 全文档、README 与代码统一按**三层**表述（`SystemAlarmLauncher.Outcome` 只有
> `SilentRequested` / `UiFallback` / `NoHandler` 三个分支）。Level 3 内部虽含多个补救动作，
> 但对外是一个层级，不再拆成 Level 4。

**这里有一个诚实的工程难题，必须讲清楚：**

`startActivity` 对 `ACTION_SET_ALARM` 是**单向的、无返回值的**。系统时钟处理完就完事，不会回传"我跳过 UI 了"还是"我弹界面了"。所以：

- 你**无法**在代码里 100% 确定 `SKIP_UI` 是否被遵守。
- 能确定的是：`startActivity` 没抛 `ActivityNotFoundException` = 至少有个 App 接住了。
- 想拿到确定结论，只能**真机实测一轮**。
  当前代码**没有**实现"厂商能力名单"这个机制（不要去找 `SkipUiCapability`，那是不存在的）。
  实测结论先记录在文档里；等实测数据积累够了再决定是否值得加常量表。

**验证方法（无需改代码，5 分钟）：**
1. 装一个 Intent 探测 App（如 `Intent Test` / `Intent Intercept`），或用本方案的调试入口。
2. 发送 `SKIP_UI=true` 的 Intent，观察是否弹出时钟界面。
3. 弹了 → 厂商忽略 `SKIP_UI` → 把该机型加入本地"已知降级名单"。
4. 没弹、且时钟 App 的闹钟列表里多了一条 → 一键成功。

### 2.4 明确区分：三种"闹钟"完全不是一回事

这是需求里最容易被混淆的点，逐个钉死：

| 维度 | 系统时钟闹钟 ✅ | App 内通知 ❌ | AlarmManager 自建 ⏰ |
|---|---|---|---|
| 实现 | `AlarmClock.ACTION_SET_ALARM` | `NotificationManager` | `AlarmManager.setAlarmClock()` |
| 响铃者 | **系统时钟 App 进程** | 系统通知栏 | **你的 App 进程** |
| 关机后是否还在 | ✅ 在（时钟 App 是系统应用） | ❌ 丢 | ⚠️ 需 `BOOT_COMPLETED` 重建 |
| 被系统杀后台 | ✅ 不受影响 | ✅ 不受影响 | ❌ 大概率不响 |
| 免打扰 / 静音 | ✅ 时钟 App 可穿透 | ⚠️ 需渠道设置为闹钟级 | ⚠️ 需自己处理 |
| 响铃音量通道 | 独立闹钟音量 | 通知音量 | 需自建 AudioTrack |
| 息屏/锁屏可响 | ✅ | ⚠️ | ⚠️ 需全屏 Intent + 厂商白名单 |
| 厂商电池优化影响 | ✅ 无 | ❌ 有 | ❌ **严重** |
| 需要的权限 | `SET_ALARM`（普通） | `POST_NOTIFICATIONS`（运行时） | `SCHEDULE_EXACT_ALARM`（Android 13+ 默认拒绝） |
| 符合本需求 | ✅ **就是这个** | ❌ 明确排除 | ❌ 明确排除 |

**结论：本方案一行 `AlarmManager` 都不用，一行 `NotificationManager` 都不用。**

理由是硬事实：国产 ROM 的电池优化会积极冻结后台进程，`AlarmManager` 在小米/华为上"闹钟不响"是社区高频问题。而系统时钟 App 是系统级预装应用，**电池优化、自启限制、后台清理基本都不碰它**。把响铃这件事外包给系统时钟，可靠度提升不是一个量级。

### 3.2 页面结构

**只有一个页面。** 不做导航、不做抽屉、不做设置页（除了一个极小的「准备入睡时长」调节项，见下）。

```
┌──────────────────────────────────────┐
│  R90 闹钟                            │  ← 顶栏
├──────────────────────────────────────┤
│                                      │
│            02:47:13                  │  ← 主时间，超大字号（等宽字体防抖）
│         2026年9月28日 周一            │  ← 日期 + 星期
│                                      │
│  准备入睡 [立即][5分][10分][■15分]→   │  ← 时长选择，横向可滚动
├──────────────────────────────────────┤
│  周期     起床时间        操作        │  ← 表头
├──────────────────────────────────────┤
│   1      04:33   今天 · 周一 [ 设置 ] │
│   2      06:03   今天 · 周一 [ 设置 ] │
│   3      07:33   今天 · 周一 [ 设置 ] │
│   4      09:03   今天 · 周一 [ 设置 ] │
│   5      10:33   今天 · 周一 [ 设置 ] │
│   6      12:03   今天 · 周一 [ 设置 ] │
│   7      13:33   今天 · 周一 [ 设置 ] │
│   8      15:03   今天 · 周一 [ 设置 ] │
│   9      16:33   今天 · 周一 [ 设置 ] │
│                                      │
└──────────────────────────────────────┘
        ↑ 消息区（Snackbar），从底部弹出
```

> 上表数值对应 §4.5 基准场景（`02:47:13` 起算，准备入睡 15 分钟，向上取整）。
> 跨天行的日期会变成 `明天 9月29日 周二` 并用强调色标出。

**关于「准备入睡」时长的调节（Q3，已确认为可调）：**

实现方式是**一排胶囊按钮**，取值 `0 / 5 / 10 / 15 / 20 / 25 / 30` 分钟，默认 15。
`0` 在界面上显示为「立即」。

- 为什么不用滑杆：躺床上时滑杆不好精确拖，胶囊是大块可点区域，盲按也能中。
- 为什么不用「长按齿轮弹滑块」：多一层交互，睡前操作越少越好；常驻一排直接可见。
- 状态用 `rememberSaveable` 持有，被系统回收重建后不丢。
- **不落盘**——本次不引入 `SharedPreferences`，保持"零存储"这个更强的隐私主张。代价是重启 App 后回到默认 15 分钟。若以后觉得烦，再加一行 `SharedPreferences` 即可（仍不算数据库）。

### 3.3 状态机

最后一列标出**当前代码是否已实现**，避免把设计当现状读。

| 状态 | 触发 | UI 表现 | 退出 | 实现状态 |
|---|---|---|---|---|
| **Normal** | App 启动 / 自然流逝 | 时间跳动，9 行可点 | — | ✅ 已实现 |
| **CrossDay**（跨天） | 某行日期 ≠ 今天 | 该行日期列显示「明天 / 后天 + 日期 + 周X」，文字用强调色 | 时间推进到该行变成"今天" | ✅ 已实现 |
| **Setting**（设置中） | 点击「设置」按钮 | 该行按钮变 loading + 禁用，其余行不变 | 成功 / 失败 / 超时 1.5s | ❌ **未实现**（当前无 loading 态） |
| **Success** | `startActivity` 未抛异常 | Snackbar：「已请求系统时钟设置 04:33」 | 数秒后自动消失 | ⚠️ 部分（只有 Snackbar，无撤销位） |

## 4. R90 计算规则

### 4.1 时间取到秒还是分 —— 建议：**内部按秒，展示按秒，闹钟按分**

| 环节 | 精度 | 理由 |
|---|---|---|
| 内部计算 | **秒（`Instant` / `ZonedDateTime`）** | 避免精度丢失，跨天判断更准 |
| 首页时钟显示 | **秒** | 需求明确要求秒级刷新 |
| 起床时间显示 | **分钟** | 秒对起床时间无意义，显示秒反而干扰阅读 |
| 传给系统闹钟 | **分钟** | API 只收 `EXTRA_HOUR` + `EXTRA_MINUTES`，秒无处可放 |

**关键取舍：起床时间的秒数怎么处理？—— 已定：向上取整**

示例：现在 `02:47:13`，+15 分钟 = `03:02:13`，+1 周期（90 分钟）= `04:32:13`。

| 口径 | `04:32:13` 显示为 | 与真实周期点的偏差 |
|---|---|---|
| 截断（向下取整） | `04:32` | 闹钟早响，最多早 59 秒 |
| **向上取整（已采纳）** | `04:33` | 闹钟晚响，最多晚 59 秒 |

**结论：采用向上取整。** 用户在 2026-09-28 明确指定，给出的判据是「`04:32:59` 就按 `04:33` 来」。

**这个选择的代价，如实说明：**

- 向上取整 = 闹钟比"真实起床点"晚响最多 59 秒。极端情况下（如真实周期点 `04:32:01`），闹钟会落在 `04:33:00`，晚了 59 秒。
- 从 R90 的睡眠科学角度，**截断其实更保守**（早醒比晚醒安全，不容易正好卡在周期末尾）。
- 所以这是一次**用一点点睡眠科学上的保守性，换「不早响、不被闹钟提前 1 分钟叫醒」的直觉一致性**的取舍。1 分钟以内对睡眠结构没有可测量的影响，属于可接受的偏好选择。

**向上取整引入的两个陷阱（代码里必须处理，否则出 bug）：**

1. **分钟进位到 60。** 若真实时间是 `04:59:30`，直接写 `minute + 1` 会得到非法的 `04:60`。
   正确做法是让 `java.time` 处理进位：

   ```kotlin
   val rounded = wake.truncatedTo(ChronoUnit.MINUTES).plusMinutes(1)
   // 04:59:30 -> truncated 04:59 -> plusMinutes(1) -> 05:00  ✅ 自动进位
   ```

2. **取整可能把时间推到下一天，`dayDiff` 必须跟着重算。**
   若真实周期点是 `23:59:30`，取整后是**次日** `00:00`。此时若还用取整前的时间算 `dayDiff`，会算出 0，UI 就会显示"今天"——而闹钟其实设在明天 00:00，直接误导用户。

   ```kotlin
   // ❌ 错误：用原始时间算
   val dayDiff = DAYS.between(today, wake.toLocalDate())

   // ✅ 正确：用取整后的时间算
   val dayDiff = DAYS.between(today, rounded.toLocalDate())
   ```

   在全部 3888 个采样组合里有 1242 个（31.9%）跨天，说明跨天不是边角场景，这个坑必须堵。

> 如果你希望闹钟精确对齐到秒——**做不到**，系统闹钟 API 只有分钟粒度。这是硬限制。向上取整同样受这条限制。

### 4.2 午夜跨天处理

**不要用「小时数是否小于 24」这种土办法。** 正确做法是用 `java.time` 做日期比较：

```kotlin
val now = ZonedDateTime.now()
val wake = now.plusMinutes(fallAsleepMinutes.toLong()).plusMinutes(90L * cycles)

// 先做向上取整
val rounded = if (wake.second == 0) wake
              else wake.truncatedTo(ChronoUnit.MINUTES).plusMinutes(1)

// 日期差：0=今天 1=明天 2=后天
// ⚠️ 必须用 rounded，不能用 wake —— 取整可能把时间推到次日
val dayDiff = ChronoUnit.DAYS.between(now.toLocalDate(), rounded.toLocalDate()).toInt()
```

`ChronoUnit.DAYS.between` 会自动处理月末、年末、闰年、闰秒边界。手写 `day + 1` 会在 12 月 31 日、2 月 28 日翻车。

**相对日期文案规则：**

| dayDiff | 主文案 | 副文案 |
|---|---|---|
| 0 | `今天` | `周X` |
| 1 | `明天` | `M月d日 周X` |
| 2 | `后天` | `M月d日 周X` |
| ≥ 3 | `M月d日` | `周X` |

**注意：dayDiff 理论上限。**

9 周期 = 15 分 + 810 分 = 825 分 = **13 小时 45 分**。

从一天中**最晚**的时刻起算（23:59:59），起床时间落在次日 13:44:59，取整后 13:45，dayDiff = 1。
所以**在"准备入睡 = 15 分钟"这个前提下，dayDiff 只可能是 0 或 1。**（上限 30 分钟时同理，仍只到 1。）

**但代码仍要写全 0/1/2/≥3 四档。** 理由：

- `fallAsleepMinutes` 可调，上限被拉高后就能触及 2。
- 要让 dayDiff 达到 2，需 `ceil(已过分钟 + fall + 810) ≥ 2880`。
  最极端起点 23:59:59，代入得 **`fall ≥ 630` 分钟（10.5 小时）**。
- **注意这个门槛是 630，不是 631。** 因为向上取整会把 `2879.0x` 顶到 `2880`：
  起点 `23:59:59`、`fall = 630` 时，原始起床点是次日 `23:59:59`，取整后变成**第三天 `00:00`**，dayDiff = 2。
  若换回截断口径，同参数只会停在 `23:59`，dayDiff = 1 —— 这是取整方式改变的副产物，容易算错。

**结论：防御性写全四档。** MVP 允许的 `fall` 上限是 30 分钟，离 630 分钟极远，所以实际界面上看不到"后天"。这不是 bug，是量级决定的。若将来把 fall 放到 630 分钟以上，才会真的出现"后天"。

### 4.3 12/24 小时制处理

**三处都要处理，容易漏：**

| 处 | 规则 |
|---|---|
| **首页时钟显示** | 跟随系统。用 `DateFormat.is24HourFormat(context)` 判断 |
| **起床时间显示** | **必须跟随系统**，否则用户看到 24 小时制的主时间 + 12 小时制的起床时间会懵 |
| **传给系统闹钟的 `EXTRA_HOUR`** | **永远传 0–23 的钟点值**，与系统 12/24 制设置无关 |

**官方对 `EXTRA_HOUR` 的定义只有一句：** 「The hour of the alarm. Used by ACTION_SET_ALARM. The value is an Integer and **ranges from 0 to 23**.」

官方**没有明说**这是"24 小时制"。措辞只给了取值范围。实际上：

- AOSP DeskClock 的 `HandleApiCalls` 实现按 0–23 直接解析（这是事实依据）。
- 传 0–23 是唯一安全的做法：12 小时制下传 `2` 表示凌晨 2 点，传 `14` 在 24 小时解释下是下午 2 点——两者不冲突，因为 0–23 是超集。

**关于 `EXTRA_IS_PM`——不要传。** 见下方修正说明。

> **⚠️ 已在代码中修正的错误**：初版本方案建议"12 小时制设备补传 `EXTRA_IS_PM` 作双保险"。这是**错误的**。
> 官方文档对 `EXTRA_IS_PM` 的原文是：`"android.intent.extra.alarm.IS_PM"`，**Used by `ACTION_DISMISS_ALARM`**（用于按时间搜索要 dismiss 的闹钟）。
> 它**不属于** `ACTION_SET_ALARM` 的参数集。传它属于非标准用法，多数实现忽略，个别实现可能误解析。
> **正确做法是：不传 `EXTRA_IS_PM`，只传 0–23 的 `EXTRA_HOUR` + `EXTRA_MINUTES`。**

**显示格式化：**

```kotlin
val formatter = DateTimeFormatter.ofPattern(
    if (DateFormat.is24HourFormat(context)) "HH:mm" else "h:mm"
)
```
注意 12 小时制用 `h:mm`（不补零），24 小时制用 `HH:mm`（补零）。不要用 `hh` —— 那是 12 小时制补零，会出现 `04:32` 这种在 12 小时制下很怪的结果。

**设备侧 12 小时制下要注意：** 把起床时间交给系统时钟后，时钟 App 会按**它自己**的系统设置显示（12 或 24 小时制），这跟你的 App 显示无关。你传的是 0–23 的绝对钟点，时钟 App 负责本地化展示。**这是正确行为，不需要干预。**

### 4.4 时区变化处理

**这是最容易被忽略的场景，但对你很关键**——你常年在太原（东八区）和南昌（东八区）两地跑，同一个时区，问题不大。但如果：

- 坐飞机跨时区
- 系统时区被手动改
- 手机从网络时间切到手动时间

**设计原则：不缓存任何绝对时间戳。**

```kotlin
// ✅ 每次心跳都重新取系统当前时间
val now = ZonedDateTime.now()

// ❌ 绝对不要这样
// val baseTime = System.currentTimeMillis()  // 存下来，后面靠差值算
```

理由：`ZonedDateTime.now()` 每次读的是系统当前时区，时区一变，下一秒就自动跟上。如果缓存了 `System.currentTimeMillis()` 做基准，时区切换后所有起床时间都会算错。

**起床时间的表达：**

```kotlin
// 起床时间的"绝对时刻"用 Instant 表达，跨时区依然准确
val wakeInstant: Instant = wake.toInstant()
```

`Instant` 是 UTC 上的一个点，不随时区漂移。显示时再转回本地时区。这样即使在飞机上开着 App，也不会出现"闹钟设在 3 小时后"实际变成了 11 小时后。

**额外的时区监听（可选但推荐）：**

```kotlin
// 注册系统时区变更广播，切时区时立即重算
val filter = IntentFilter().apply {
    addAction(Intent.ACTION_TIMEZONE_CHANGED)
    addAction(Intent.ACTION_TIME_CHANGED)
    addAction(Intent.ACTION_DATE_CHANGED)
}
```

不过因为有 1 秒心跳，最坏情况 1 秒内 UI 就自动修正了，**这个广播监听不是必须的**。我倾向不加——少一个 `BroadcastReceiver` 少一份维护负担。心跳已经覆盖了。

**取整跨天场景（⚠️ 最容易被写错的一个）：当前时间 2026-09-28（周一）22:14:30，准备入睡 15 分钟。**

基准点 `23:45:00`，1 周期 = 次日 `01:15:00`（整分，不进位），日期 `2027-01-01`。`ChronoUnit.DAYS.between` 会正确算出 dayDiff=1，**不要自己写日期加一天**。

|---|---|---|
| 默认 | 主色填充胶囊，白字「设置」 | ✅ |
| 按下 | 主色加深 12%，轻微缩放 0.97 | ✅ |
| 设置中（该行） | 显示 16dp `CircularProgressIndicator`，替换文字 | ❌ |
| 设置中（其他行） | 保持默认外观 | ✅（允许并发，但实际会有互斥锁） |
| 命中厂商降级名单 | 文案改「在时钟中确认」 | ✅ |
| 全局错误（找不到时钟） | 全部按钮禁用 + 变灰 | ❌ |

**关于「设置中」的超时：** `startActivity` 是同步返回的（要么抛异常要么立即返回），所以「设置中」状态实际上只持续几毫秒。**为了不让 loading 一闪而过（视觉噪点），建议强制保持 300ms 最短显示时长**，或者干脆去掉 loading 态，直接靠 Snackbar 反馈。

> 我倾向**去掉 loading 态**。`startActivity` 立刻返回，加 loading 是虚假的仪式感。Snackbar 已经够了。

### 5.5 暗色模式 / 大字体 / 单手操作

**暗色模式：**

- 用 Compose 的 `dynamicDarkColorScheme` / `dynamicLightColorScheme`（Android 12+ 跟随壁纸取色）或自定义 `darkColorScheme`。
- `themes.xml` 里 `Theme.Material3.DayNight.NoActionBar`，跟随系统。
- **不要在暗色下用纯黑 `#000000`。** 用 `#121212` 或 Material 3 的 `surface`，纯黑在 OLED 上滚动会有拖影感。
- **主时间不要用纯白 `#FFFFFF`**，用 `#E6E1E5` 级别的浅灰，夜间不刺眼。

**大字体：**

- 全部用 `sp` 不用 `dp` 写字号，跟随系统字体缩放。
- 布局用 `weight` 和 `wrapContentHeight`，不要写死高度。
- **测试方法**：系统设置把字体调到「最大」，进 App 检查 9 行是否还能正常显示、按钮是否被裁切。这是必测项。

**单手操作：**

| 措施 | 说明 |
|---|---|
| 按钮在下半屏 | 9 行列表占据了屏幕下半部，天然满足 |
| 行高 ≥ 64dp | 超出 48dp 最小触控区要求 |
| 整行可点 | 不用精确瞄按钮 |
| 主时间不可点 | 避免误触（不需要交互） |
| 齿轮放右上角 | 低频操作，放角落 |
| 无底部导航栏 | 只有一个页面，不需要 |

**额外建议：**

- **屏幕常亮？不要。** 睡眠场景下常亮会干扰入睡，而且费电。App 进后台就停止心跳（Compose 的 `LaunchedEffect` 会自动做）。
- **不要在睡前弹任何对话框。** 唯一会弹的对话框是 NoClockApp 错误态，那是必须的。
- **Snackbar 从底部弹出**，位置在拇指区，方便划掉。

## 6. Android 关键实现

### 6.1 权限

**只需要一个：**

```xml
<uses-permission android:name="com.android.alarm.permission.SET_ALARM" />
```

这是**普通权限（normal protection level）**，安装时自动授予，**不会弹权限对话框**，用户也无法撤销。这是这个 App 能做到「零弹窗」的根本原因。

**明确不需要的权限（一个都不加）：**

| 权限 | 为什么不需要 |
|---|---|
| `INTERNET` | 不联网。**不加这个权限是最强的隐私承诺**——系统层面就断网了 |
| `ACCESS_NETWORK_STATE` | 同上 |
| `POST_NOTIFICATIONS` | 不做通知（Android 13+ 需运行时申请，能省则省） |
| `SCHEDULE_EXACT_ALARM` | 不自己设闹钟（Android 13+ 默认拒绝，能省则省） |
| `USE_EXACT_ALARM` | 同上 |
| `RECEIVE_BOOT_COMPLETED` | 不监听开机 |
| `WAKE_LOCK` | 不常驻 |
| `VIBRATE` | 不自己震动 |
| `READ/WRITE_EXTERNAL_STORAGE` | 不碰文件 |
| `QUERY_ALL_PACKAGES` | 用精确 `<queries>` 替代（见 6.5） |

> **「不申请 `INTERNET` 权限」是这个方案对"不收集隐私"最强的技术背书。** 不是"我们承诺不传数据"，而是"这个 App 在系统层面就没有联网能力"。装完可以用 `adb shell dumpsys package com.yanfei.r90alarm | grep INTERNET` 自证——空输出。

**三个容易翻车的点：**

1. **`<queries>` 必须写。** Android 11+ 不写的话，`packageManager.resolveActivity()` 对不认识的应用一律返回 `null`，你的 App 会误报"没有系统时钟"。这是最经典的坑。
2. **`android:exported="true"` 必须写。** targetSdk 31+ 有 intent-filter 的组件不写这个属性**装不上**，报 `INSTALL_PARSE_FAILED_MANIFEST_MALFORMED`。
3. **不要用 `<queries><package android:name="..."/></queries>` 硬编码厂商包名。** 用 `<intent>` 形式，跨厂商通用。硬编码包名会在换手机时失效。

**`data_extraction_rules.xml`（Android 12+ 备份规则，`allowBackup=false` 时其实可省，但写了更明确）：**

```xml
<?xml version="1.0" encoding="utf-8"?>
<data-extraction-rules>
    <cloud-backup>
        <exclude domain="sharedpref" path="." />
    </cloud-backup>
</data-extraction-rules>
```

#### 6.3.1 R90 计算核心（`R90Calculator.kt`）

```kotlin
package com.yanfei.r90alarm

import java.time.ZonedDateTime
import java.time.Instant
import java.time.temporal.ChronoUnit

/**
 * R90 睡眠周期计算。
 *
 * 设计原则：
 * 1. 每一次计算都基于"当前这一刻"，不缓存时间基准 —— 时区/时间变更自动跟上。
 * 2. 起床时刻用 Instant 表达（时区无关），显示时再转本地时区。
 * 3. 日期差用 ChronoUnit.DAYS.between，不手写日期加减。
 */
object R90Calculator {

    /** 单个睡眠周期的分钟数。R90 = 90 分钟。 */
    const val CYCLE_MINUTES = 90

    /** 准备入睡时长默认值（分钟）。v0.1 起已可由用户调节，这只是初始值。 */
    const val DEFAULT_FALL_ASLEEP_MINUTES = 15

    /** 「准备入睡」可选项（分钟）。0 表示躺下即睡。 */
    val FALL_ASLEEP_OPTIONS = listOf(0, 5, 10, 15, 20, 25, 30)

    /** 支持的周期数范围 */
    val CYCLES = 1..9

    /**
     * 计算结果。
     *
     * @param cycles      周期数 1..9
     * @param wakeTime    起床时间的原始时刻（本地时区，含秒）—— 仅供展示"真实周期点"
     * @param wakeInstant 起床时刻的绝对时间（时区无关）
     * @param hour24      取整后的钟点 0..23（直接传给系统闹钟）
     * @param minute      取整后的分钟 0..59（直接传给系统闹钟）
     * @param dayDiff     与"今天"相差的天数：0=今天 1=明天 2=后天 ...
     *                    ⚠️ 基于【取整后】的日期计算，不是原始时刻
     * @param isCrossDay  是否跨天（dayDiff > 0）
     * @param hasSubMinutePrecision 原始时刻是否含非零秒（含则说明显示值经过进位）
     */
    data class Result(
        val cycles: Int,
        val wakeTime: ZonedDateTime,
        val wakeInstant: Instant,
        val hour24: Int,
        val minute: Int,
        val dayDiff: Int,
    ) {
        val isCrossDay: Boolean get() = dayDiff > 0
        val hasSubMinutePrecision: Boolean get() = wakeTime.second != 0
    }

    /**
     * 计算所有 1..9 周期的起床时间。
     *
     * @param now 当前时刻。由调用方传入，便于单元测试注入固定时间。
     * @param fallAsleepMinutes 准备入睡时长，默认 15。
     */
    fun calculateAll(
        now: ZonedDateTime,
        fallAsleepMinutes: Int = DEFAULT_FALL_ASLEEP_MINUTES,
    ): List<Result> {
        require(fallAsleepMinutes >= 0) {
            "准备入睡时长不能为负，实际 $fallAsleepMinutes"
        }

        val today = now.toLocalDate()

        return CYCLES.map { cycles ->
            val wake = now
                .plusMinutes(fallAsleepMinutes.toLong())
                .plusMinutes(CYCLE_MINUTES.toLong() * cycles)

            // 向上取整：秒非 0 就进位到下一分钟。
            //
            // ⚠️ 不能写 wake.minute + 1：
            //    04:59:30 会算出非法的 04:60。
            //    用 truncatedTo(MINUTES).plusMinutes(1) 让 java.time 处理进位，
            //    04:59:30 -> 04:59 -> 05:00，且 23:59:30 -> 次日 00:00 也自动跨天。
            val rounded = if (wake.second == 0) {
                wake
            } else {
                wake.truncatedTo(ChronoUnit.MINUTES).plusMinutes(1)
            }

            // ⚠️ dayDiff 必须用 rounded 算，不能用 wake：
            //    取整会把 23:59:30 推到次日 00:00，用 wake 算会得到 dayDiff=0，
            //    UI 就会显示"今天"而闹钟其实设在明天 —— 直接误导用户。
            val dayDiff = ChronoUnit.DAYS
                .between(today, rounded.toLocalDate())
                .toInt()

            Result(
                cycles = cycles,
                wakeTime = wake,
                wakeInstant = wake.toInstant(),
                hour24 = rounded.hour,
                minute = rounded.minute,
                dayDiff = dayDiff,
            )
        }
    }

    /**
     * 人类可读的相对日期文案。
     *
     * MVP 的 fall 上限是 30 分钟，dayDiff 最大只会到 1；
     * 但四档仍写全 —— fall 放到 630 分钟以上就会出现"后天"（见 §4.2）。
     */
    fun relativeDayLabel(dayDiff: Int): String = when (dayDiff) {
        0 -> "今天"
        1 -> "明天"
        2 -> "后天"
        else -> "第 ${dayDiff + 1} 天"
    }
}
```

> 以上为结构摘录（**注释措辞可能与源码略有出入，属正常**）。
> 权威版本是 `app/src/main/java/com/yanfei/r90alarm/R90Calculator.kt`。
> 算法与取值已对齐，并被 29 个 JVM 单元测试覆盖（含进位到小时、进位跨天、dayDiff 跟随等边界）。

#### 6.3.2 系统闹钟调用（`SystemAlarmLauncher.kt`）

```kotlin
object SystemAlarmLauncher {

    private const val ALARM_LABEL = "R90 闹钟"

    sealed interface Outcome {
        /** Level 1：已请求静默。注意无法确认厂商是否真的跳过了界面。 */
        data class SilentRequested(
            val hour24: Int, val minute: Int,
            val handler: String?, val elapsedMs: Long,
        ) : Outcome

        /** Level 2：已打开系统时钟并预填，等用户按保存。 */
        data class UiFallback(
            val hour24: Int, val minute: Int,
            val handler: String?, val elapsedMs: Long,
        ) : Outcome

        /** Level 3：设备上没有任何 App 能处理 SET_ALARM。 */
        data class NoHandler(val reason: String, val handler: String?) : Outcome
    }

    fun setAlarm(
        activity: Activity, hour24: Int, minute: Int, preferSilent: Boolean = true,
    ): Outcome {
        require(hour24 in 0..23); require(minute in 0..59)

        if (preferSilent) {
            val silent = tryLaunch(activity, hour24, minute, skipUi = true)
            if (silent.state == LaunchState.OK) {
                return Outcome.SilentRequested(hour24, minute, silent.handler, silent.elapsedMs)
            }
            // 静默失败就降级，不直接报错
        }

        val fallback = tryLaunch(activity, hour24, minute, skipUi = false)
        return when (fallback.state) {
            LaunchState.OK -> Outcome.UiFallback(hour24, minute, fallback.handler, fallback.elapsedMs)
            LaunchState.NO_HANDLER -> Outcome.NoHandler("no-handler", fallback.handler)
            LaunchState.ERROR -> Outcome.NoHandler("error:${fallback.error}", fallback.handler)
        }
    }

    private fun tryLaunch(
        activity: Activity, hour24: Int, minute: Int, skipUi: Boolean,
    ): TryResult {
        val intent = buildIntent(hour24, minute, skipUi)

        // 先探测：Android 11+ 不配 <queries> 时这里会误返回 null
        val resolved = intent.resolveActivity(activity.packageManager)
            ?: return TryResult(LaunchState.NO_HANDLER, null, null, 0L)

        val t0 = System.currentTimeMillis()
        return try {
            activity.startActivity(intent)
            TryResult(LaunchState.OK, resolved.flattenToShortString(), null,
                System.currentTimeMillis() - t0)
        } catch (_: ActivityNotFoundException) {
            // 竞态：resolveActivity 通过但 startActivity 时应用被禁用/卸载
            TryResult(LaunchState.NO_HANDLER, resolved.flattenToShortString(),
                "ActivityNotFoundException", System.currentTimeMillis() - t0)
        } catch (_: SecurityException) {
            // 极少数 ROM 会对 SET_ALARM 做额外校验
            TryResult(LaunchState.ERROR, resolved.flattenToShortString(),
                "SecurityException", System.currentTimeMillis() - t0)
        } catch (e: Exception) {
            // 兜底。刻意接住异常对象 —— 类名要写进诊断日志
            TryResult(LaunchState.ERROR, resolved.flattenToShortString(),
                e.javaClass.simpleName, System.currentTimeMillis() - t0)
        }
    }

    private fun buildIntent(hour24: Int, minute: Int, skipUi: Boolean): Intent =
        Intent(AlarmClock.ACTION_SET_ALARM).apply {
            // 关键：不传 EXTRA_HOUR 时 SKIP_UI 会被系统忽略（官方文档明示）。
            putExtra(AlarmClock.EXTRA_HOUR, hour24)
            putExtra(AlarmClock.EXTRA_MINUTES, minute)
            putExtra(AlarmClock.EXTRA_MESSAGE, ALARM_LABEL)
            putExtra(AlarmClock.EXTRA_SKIP_UI, skipUi)

            // ⚠️ 刻意不传 EXTRA_IS_PM（官方用途是 ACTION_DISMISS_ALARM，不是 SET_ALARM）。
            // 不传 EXTRA_DAYS / EXTRA_RINGTONE / EXTRA_VIBRATE —— 一次性闹钟，用系统默认。
        }

    /** Level 3 的补救动作之一：打开系统时钟的闹钟列表页（无需权限）。 */
    fun openAlarmList(context: Context): Boolean { /* 见源码 */ }
}
```

/**
 * 从任意 Context 向上找宿主 Activity。
 *
 * 不要写 context as ComponentActivity —— Compose 拿到的 Context 常被
 * ContextThemeWrapper 包过一层，直接强转在部分 ROM 上会 ClassCastException 崩溃。
 */
private fun Context.findActivity(): Activity? {
    var ctx: Context = this
    while (ctx is ContextWrapper) {
        if (ctx is Activity) return ctx
        ctx = ctx.baseContext
    }
    return null
}

/**
 * 秒级心跳。
 *
 * 对齐整秒，而不是 delay(1000)：后者每次循环实际耗时略多于 1000ms，
 * 误差累积几小时后秒数会肉眼可见地漂到与系统时间不符。
 *
 * 外层套 repeatOnLifecycle(RESUMED)：退到后台 / 熄屏就停心跳。
 * 否则躺下后把 App 放后台，一夜要空转 2.8 万次，白耗电且容易被厂商省电策略盯上。
 */
@Composable
private fun rememberTickingNow(): State<ZonedDateTime> {
    val now = remember { mutableStateOf(ZonedDateTime.now()) }
    val lifecycleOwner = LocalLifecycleOwner.current
    LaunchedEffect(lifecycleOwner) {
        lifecycleOwner.repeatOnLifecycle(Lifecycle.State.RESUMED) {
            while (true) {
                val current = ZonedDateTime.now()
                now.value = current
                delay((1000L - current.nano / 1_000_000L).coerceIn(1L, 1000L))
            }
        }
    }
    return now
}

@OptIn(ExperimentalMaterial3Api::class)

        // Level 3 补救对话框：① 打开时钟列表 ② 去应用管理查是否被禁用 ③ 复制时间

            NoClockAppDialog(

### 6.4 如何处理 ActivityNotFoundException

**分三层，缺一不可：**

**第一层：先 `resolveActivity` 探测（预防）**

```kotlin
if (intent.resolveActivity(packageManager) == null) {
    // 直接走降级或报错，不调 startActivity
    return LaunchResult.NO_HANDLER
}
```

好处：不触发异常，性能更好（异常构造有栈开销）。

**第二层：`try/catch` 兜底（处理竞态）**

`resolveActivity` 返回非 null 到 `startActivity` 之间，理论上存在应用被禁用/卸载的窗口。虽然极窄，但必须抓：

```kotlin
try {
    activity.startActivity(intent)
    LaunchResult.OK
} catch (e: ActivityNotFoundException) {
    LaunchResult.NO_HANDLER
} catch (e: SecurityException) {
    LaunchResult.ERROR
} catch (e: Exception) {
    LaunchResult.ERROR
}
```

`SecurityException` 单独抓的理由：极少数 ROM 会对 `SET_ALARM` 做额外校验（比如企业设备策略），抛的是 `SecurityException` 而不是 `ActivityNotFoundException`。

**第三层：UI 必须给出「为什么 + 怎么办」**

失败时**不能只显示"设置失败"**。必须同时给出：

1. **原因**：`找不到系统时钟应用（可能有 App 能处理但没有，或被系统禁用）`
2. **三个补救路径**（每个都是可执行的具体动作）：
   - 打开系统时钟闹钟列表（`ACTION_SHOW_ALARMS`）→ 用户手动设
   - 打开系统「应用管理」→ 检查时钟是否被禁用
   - 复制时间到剪贴板 → 用户去别处手动设

**为什么必须给三个而不是一个：** 不同失败原因对应不同补救。若是"时钟被禁用"，需要路径 2；若是"ROM 精简了时钟"，需要路径 1 或 3。单一路径会让人卡死。

### 6.5 Android 11+ 包可见性

**问题：** Android 11（API 30）起，`PackageManager` 默认只能"看见"自己 App、系统预装、以及通过 `<queries>` 显式声明的应用。不声明的话：

```kotlin
intent.resolveActivity(packageManager)  // 永远返回 null，即使系统时钟明明存在
```

**后果：** 你的 App 会误判"没有系统时钟应用"，走到错误分支。**这是最隐蔽的坑，因为真机上时钟 App 就在那儿，你却报"找不到"。**

**解法：** 在 `<manifest>` 里用 `<queries>` 声明需要的 action：

```xml
<queries>
    <intent>
        <action android:name="android.intent.action.SET_ALARM" />
    </intent>
    <intent>
        <action android:name="android.intent.action.SHOW_ALARMS" />
    </intent>
</queries>
```

**为什么用 `<intent>` 而不是 `<package>`：**

| 写法 | 问题 |
|---|---|
| `<package android:name="com.android.deskclock" />` | 硬编码包名，小米/华为/三星的时钟包名全不一样，换个手机就失效 |
| `<intent><action .../></intent>` ✅ | 按能力声明，"谁能处理 SET_ALARM 谁就可见"，跨厂商通用 |

**要不要 `QUERY_ALL_PACKAGES`？** **绝对不要。** 那是"看见所有应用"的权限，Google Play 会审核是否必要，而且与"不收集隐私"的定位直接冲突。两个 `<intent>` 就够了。

**验证包可见性是否生效（真机命令）：**

```bash
# 看你的 App 实际被授予了哪些可见包
adb shell dumpsys package com.yanfei.r90alarm | grep -A 20 "queries"
```

**构建期已踩到并修掉的五个真实阻断（记下来备用）：**

1. **`build.gradle.kts` 用了 `#` 注释** —— Kotlin DSL 只认 `//`，脚本编译直接报 `Unresolved reference`。
2. **Kotlin 2.0 起 Compose 编译器独立成插件** —— 必须显式声明 `org.jetbrains.kotlin.plugin.compose`，否则 `compose = true` 直接报错。
3. **`local.properties` 的反斜杠转义** —— 写成 `D\:\Android\Sdk` 会被 Java properties 解析成 `D:AndroidSdk`（`\A`、`\S` 的转义符被吞），
   AGP 的 `SdkLocator.validateSdkPath` 抛 `IOException: 文件名、目录名或卷标语法不正确`。
   正确写法用正斜杠：`sdk.dir=D:/Android/Sdk`。
4. **2 个单元测试断言未跟随取整口径** —— 仍断言 `04:32` / `01:44`，改为 `04:33` / `01:45`。
5. **测试结果假阳性** —— `testDebugUnitTest` 显示 `BUILD SUCCESSFUL` 且报告里 `tests="27"`，
   但那 27 个是**改代码之前**留下的旧报告，源码根本没被重跑。修法：验证时必须加 `--rerun-tasks --no-build-cache`，
   并把报告 XML 里的 `timestamp` 与测试源码 mtime 比对。

**关于非 ASCII 路径 —— 这里有一个我修正过的错误结论：**

早期实测发现 `assembleDebug` 在中文路径下 `BUILD SUCCESSFUL`，于是我写下「AGP 的非 ASCII 路径警告是假警报，不必搬家」。
**这个结论只对了一半。** 第 5 条（缓存假阳性）被拆穿后强制重跑，真相才出来：

| 任务 | 中文路径目录 | ASCII 路径目录 |
|---|---|---|
| `assembleDebug` | ✅ `BUILD SUCCESSFUL` | ✅ `BUILD SUCCESSFUL` |
| `testDebugUnitTest --rerun-tasks --no-build-cache` | ❌ `BUILD FAILED`，`ClassNotFoundException`，1 test failed | ✅ `tests="29" failures="0"` |

**根因**：Gradle 的测试 worker 在 Windows 上以命令行参数传 classpath，非 ASCII 路径在这一环被破坏。
与代码无关，是 Gradle/Windows 层面的限制。

**结论**：`assembleDebug` 不受中文路径影响，**但只要有单元测试，工程就必须放纯 ASCII 路径**。
`android.overridePathCheck=true` 只能让警告闭嘴，解决不了测试挂掉。本项目正本因此定在纯 ASCII 目录下。
