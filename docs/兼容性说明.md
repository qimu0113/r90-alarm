# R90 闹钟 · 兼容性说明

> 口径：**已实测** = 在本机（PMB110 / ColorOS 16.0.9.400 / Android 16）真实跑出来的；
> **已核对** = 逐条对照 Android 官方文档；**推测** = 无权威来源、本机无法验证，仅供参考。
>
> 整理日期：2026-10-03

---

## 一、一句话结论

- **系统版本**：覆盖 **Android 8.0（API 26）及以上**，覆盖 2026 年在用安卓机的绝大多数。
- **真正的变数只有一个**：厂商时钟 App 是否遵守 `EXTRA_SKIP_UI`（一键无界面）。
- **无论厂商遵不遵守，App 都不会"点了没反应"** —— 三条路径（无界面 / 预填待保存 / 给补救方案）总有一条能走通。

---

## 二、API 层面（硬事实，逐条已核对官方文档）

本项目用到的每一项系统能力，及其最低可用版本：

| 用到的能力 | 最低 API | 在 minSdk 26 下 | 备注 |
|---|---|---|---|
| `AlarmClock.ACTION_SET_ALARM` | 9 | ✅ 可用 | 设置闹钟的入口 |
| `EXTRA_HOUR` / `EXTRA_MINUTES` / `EXTRA_MESSAGE` | 9 | ✅ 可用 | 时间与标签 |
| `EXTRA_SKIP_UI` | **11** | ✅ 可用 | 「请跳过界面」，**是请求不是命令** |
| `AlarmClock.ACTION_SHOW_ALARMS` | **19** | ✅ 可用 | Level 3 补救：打开闹钟列表。**注意不是 API 9** —— 官方指南写明 "available for Android 4.4 (API level 19) and higher" |
| 权限 `com.android.alarm.permission.SET_ALARM` | 9 | ✅ 可用 | **normal 级**，安装即授予，**不弹窗** |
| `java.time`（`ZonedDateTime` / `ChronoUnit`） | **26** | ✅ 可用 | **minSdk 定 26 的唯一理由**，省掉 desugaring |
| `<queries>` 包可见性 | 30 起强制 | ✅ 已声明 | 26–29 上声明了也无害 |
| Compose / Material3 / androidx.* | 由各库自身 minSdk 决定 | ✅ 可用 | 本项目用的版本要求均 ≤ 26 |

**推论**：`minSdk 26` = Android 8.0，这是**主动选择**而不是将就 —— 低一档到 21 就要开 `coreLibraryDesugaring`，APK 变大、构建变复杂，为了一个自用工具不值得。

## 三、设备 / ROM 层面（真正需要关心的地方）

兼容性的关键不在 Android 版本，而在**设备上那个时钟 App 是谁写的**。

| 分支 | 触发条件 | 用户看到什么 | 状态 |
|---|---|---|---|
| ① 时钟存在 + 遵守 `SKIP_UI` | 如 ColorOS、AOSP/Google 时钟 | **无界面，闹钟直接设好** | ✅ **本机已实测** |
| ② 时钟存在 + 忽略 `SKIP_UI` | 部分国产 ROM | 自动弹出时钟页、时间已预填，**用户按一次保存** | 设计内降级（Level 2），本机无法复现 |
| ③ 时钟缺失 / 被禁用 | 极简 ROM、部分平板、Android TV | 弹对话框：说明原因 + 给 3 条补救路径 | 代码就绪，本机未复现 |

> 分支 ③ 的三条补救路径：打开系统时钟列表 / 去应用管理检查时钟是否被禁用 / 复制时间手动设。

## 六、不兼容 / 做不到的地方（诚实清单）

| 限制 | 原因 |
|---|---|
| 闹钟**精度只到分钟** | `SET_ALARM` 只收 `EXTRA_HOUR` + `EXTRA_MINUTES`，秒无处安放 |
| **无法读取或删除**系统时钟里的闹钟 | ColorOS 的 `ClockProvider` 要求系统级权限 `oppo.permission.OPPO_COMPONENT_SAFE`，App 与 adb shell 都拿不到；也没有 `ACTION_DELETE_ALARM` 这类接口 |
| **无法确认**是否真的无界面 | `startActivity` 是单向的，系统时钟不回传结果。App 永远无法自证"已静默设置" |
| 无系统时钟的设备上无法工作 | 只能给补救方案（Level 3） |

## 七、怎么自己复测（换机 / 换 ROM 后）

### 推荐做法：用 App 自带的诊断日志

不用连电脑。正常用几天，每次点「设置」都会记一条。用完之后点右上角 ⓘ → 「导出」即可。

要看的是日志里的两个字段：

| 字段 | 含义 |
|---|---|
| `level=1` / `level=2` / `level=3` | 这次走的是哪条路径（请求静默 / 弹了界面 / 找不到时钟） |
| `判定=无界面(...)` / `判定=有界面(...)` | 本 App 在点击后被暂停了多久 —— 间接反映时钟界面弹没弹 |

**关键**：`level=1` 只代表「静默请求发出去了」，**不代表厂商遵守了**。真正的地面实况在 `判定=`。
`level=1` 且 `判定=无界面` → 厂商遵守；`level=1` 但 `判定=有界面` → 请求发出去了但被无视。
（判定是启发式，日志里同时保留了原始值 `ui=pause1/first=57ms/total=200ms/still=false`，以原始值为准。）

### 手动做法：用 adb 直接试

```bash
# 1. 看本机有没有能响应 SET_ALARM 的应用，以及它是谁
adb shell cmd package query-activities -a android.intent.action.SET_ALARM

# 2. 请求「无界面」设置一个 21:37 的闹钟
adb shell am start -a android.intent.action.SET_ALARM \
  --ei android.intent.extra.alarm.HOUR 21 \
  --ei android.intent.extra.alarm.MINUTES 37 \
  --es android.intent.extra.alarm.MESSAGE "兼容性自测" \
  --ez android.intent.extra.alarm.SKIP_UI true

# 3a. 若遵守 → 顶层 Activity 不变，且闹钟已落库
adb shell dumpsys alarm | grep -i "兼容性自测"
# 3b. 若不遵守 → 会弹出时钟页，需要手动确认

# 4. 收尾：进系统时钟列表手动删掉这条测试闹钟
adb shell am start -a android.intent.action.SHOW_ALARMS
```

> 判定标准：**第 3 步要看两件事** —— ① 屏幕上有没有弹时钟（用 `dumpsys window | grep mCurrentFocus` 看顶层 Activity 变没变）；② `dumpsys alarm` 里闹钟有没有落库。只看其中一条会误判。

## 八、验证边界声明

- **已实测**：ColorOS 16.0.9.400 / Android 16 上的 `SKIP_UI` 遵守情况、App 界面渲染、取整逻辑、大字体、深浅色、端到端链路、零网络权限。
- **未验证**：除 OPPO 外**所有厂商**的 `SKIP_UI` 行为（表中标"推测"的部分）；Level 2 / Level 3 两条降级路径**未在任何真机上复现过**（本机走的是 Level 1）。
- **不要**把本文件当成"全安卓都兼容"的保证。它能保证的是：**每条路径都有代码兜底，不会崩、不会静默失败**。

> **修正记录（2026-10-03）**：本文经独立复核。第二节曾把 `ACTION_SHOW_ALARMS` 的 API 等级写成 **9** —— 实际是 **API 19**（官方指南原文：*available for Android 4.4 (API level 19) and higher*）。已更正。同表其余 API 等级均复核无误。此项更正**不影响 `minSdk 26` 的结论**（19 < 26）。
